# 版本 6 与连续业务闭环正确性

本轮将身份格式、真实收报、源计数和逐字段动态更新接到 BMv2。普通版和诊断版各完成五类案例，共完整交付 1890 个业务包，独立核查 6779 个输出帧，全部 206 项单元检查通过。结果是确定性正确性证据，没有开展静态与动态方法的公平性能比较。

数据入口为 [运行与分析清单](../data/into-validation/n3-validation-01/manifest.json)。时间线提供 [PNG](../figures/into-validation/n3-validation-03/live-identity-and-transitions.png) 和 [PDF](../figures/into-validation/n3-validation-03/live-identity-and-transitions.pdf)，由普通版真实报告和字段确认生成。

## 实际接口

独立的 into_int.p4 保留原有 TT-INT 门控，不改变旧版本。基础头为 Count、InitTTL、Version、Metric 各 8 位和 FlowTag、Session 各 32 位，共 12 B。队列记录为节点、跳数各 8 位、egress 时间 48 位及队列值 32 位，共 12 B。版本为 6，每包 K=1，源端即使未插入记录也承担基础头。没有头部空间时正常转发，空遥测不导出，sink 剥离元数据后恢复原 UDP 内容和校验和。

两条业务路径为 1→3、2→3，另有独立 sink 4。Session=20，逻辑 FlowTag=1001/2002，对应寄存器槽 1/2。逻辑身份与槽索引分开，采集器直接从报告解码身份，不用 IPv4 ID 关联在线流。槽上限为 256，记录栈上限为 8，采样节点仍限制 1..8。本轮只验证两个注册流和三个采样节点，没有据格式范围宣称支持任意规模。

x 使用 TTEgress.max_count 的 0/1，θ 使用 TTEgress.time_threshold。禁用、改阈值和重新启用不清空成功时间，容量和 MTU 阻挡也不更新门控。新 Thrift 客户端记录成功和失败的实际序列化请求/回复，各字段独立确认。失败字段在付费读取实际值前处于未知状态，在线求解暂停，其他已确认字段保留。软件序号仅用于本地确认排序，没有数据面 CAS、多节点原子事务或重启恢复协议。

动态算法复用时序机会与剩余窗口修复策略，只接收实收报告、实际返回且计费的源计数、确认和已可用通知。诊断、发送日志、包 ID 和完整输入仅用于离线核对。读取捕获日志时只读取完整行并按接收时刻裁剪，不提前看到尚未收到的帧。

## 五类案例

| 案例 | 每版本业务包 | 验收内容 |
| --- | ---: | --- |
| identity | 85 | 身份、未知流、头部/记录 MTU、恰好容纳记录及旧会话 |
| continuous | 320 | 业务连续发送中的关闭、先改阈值再启用、降低阈值及状态保留 |
| partial_failure | 320 | 阈值成功、许可失败、确认延后、付费核对及真实读取错误 |
| counter_wrap | 60 | 32 位源计数回绕、流 1 停流及后续读取 |
| causal_loop | 160 | 实际报告、计数及需求通知驱动的配置变化 |

全部案例输入在运行前冻结，种子为 0。前四类是强制正确性时序，不能作为算法收益。旧会话中预装的记录是验证注入，禁止新采样且被在线采集器拒绝，不计入真实生成样本或年龄依据。源计数从 2^32−5 开始的案例最终得到流 1/2 计数 15/35，没有注入新的 48 位门控回绕检查。

partial_failure 通过不存在寄存器的真实 Thrift 请求触发写和读错误。确认延迟在本地接口延后 300 ms 提供，实际 RPC 回复时间、延迟门槛及策略可用时间分开。它没有模拟管理网络 ACK 延迟、传输断连或超时后的重连。

causal_loop 运行 10 s，前 2 s 正常执行预热，测量 [2,10) s。初态固定为 [50 ms,off,off,off]，不是静态训练配置。独立管理进程通过 UNIX 数据报提供需求，先激活对象 1，再激活对象 3。通知预定 0/3 s 发出，本轮在 1/4 s 的控制轮询中可用。两个版本都在约 6.035–6.036 s 关闭源 1，并开通节点 3 的两个流槽，各完成 3 次真实更新。

通知可用至字段变化约 2.035 s，包含通知后两次源计数观察与主机求解时间。这不是即时响应或硬延迟保证。诊断版与普通版的部分样本数不同，软件时序和诊断开销可能影响结果，不能把差异作为性能排名。

## 核对及费用

诊断版按本节点真实 egress 顺序独立重放，核对包实际读到的 θ、许可、上次成功时间、有效位、容量、MTU、队列值和源计数，再与成功 RPC 的可能生效区间及最终寄存器核对。没有把预声明更新时点当成全网原子时点。普通版核对线格式、业务恢复、计数、确认和合法观察。

| 版本 | 业务包 | 报告，含旧会话注入 | 输出帧 | 案例核对项 |
| --- | ---: | ---: | ---: | ---: |
| 诊断 | 945 | 557 | 3391 | 35037 |
| 普通 | 945 | 554 | 3388 | 20713 |

另各有 9 次闭环预测来源核对。全部已注册源计数读取实测为 81/40 B，阈值写为 94/30 B，许可写为 89/30 B。失败写、失败读和状态核对单独保留实际字节，不按正常调用长度代替。安装、冷启动、观察、更新和验证分列。

带内费用由逐链路 IPv4 增量计，导出尝试按 Ethernet 捕获长度和最小 60 B 补齐分别计，不含 FCS。控制 API、本地管理消息有效负载和 loopback 捕获帧分列，不跨层相加。控制捕获包含 CLI 镜像安装、连接、TCP、GSO 及诊断，不按收包时刻归因到单 RPC。

causal_loop 两版本的逐链路增量均为 e1/e2/e3=1548/960/3252 B，导出补齐 6660 B。这些数据费用覆盖全部业务与预热。测量窗口内控制 API 为 2293 B，即 286.625 B/s，另有 192 B 实际管理通知有效负载。192 B 只对应本轮消息结构，不是通用通知长度，也不是管理网络帧。

使用已有隔离 steady_clock BMv2。发送前至实际接收构成生成因果区间，所有案例的本地偏移区间兼容。该结果不是硬件同步或精确生成 AoI，队列值也不是事件检测效果。本轮没有输出统计监测改善或吞吐结论。

正确性限额为每案例每链路附加 20000 B、导出补齐 20000 B，每运行全量控制捕获 128 MiB。闭环使用宽松数据预算，尚未把异步通知、失败和核对准确加入预测修复账本，不能据本轮达标推出硬预算监管。性能阶段须统一静态与动态的密网格、观察接口、调参/测试隔离和全部实际成本。

首个诊断运行因初期未知速率漏记而在闭环来源检查时异常，原始失败记录保留，最终整组重新运行。没有按监测效果筛选运行或删除失败数据。

## 复现

需要本机 P4、BMv2/Thrift、Mininet、Scapy、Matplotlib、NumPy、Times New Roman 及 pdffonts，交换机使用已有隔离单调时钟构建。所有输出目录必须不存在。脚本只清理本次创建的网络和进程。

~~~bash
python3 experiments/build_into.py
python3 experiments/build_into.py --diagnostics
python3 -m unittest discover -s tests -v
sudo python3 experiments/run_into_validation.py \
  --output data/into-validation-runs/新的诊断目录
sudo python3 experiments/run_into_validation.py --ordinary \
  --output data/into-validation-runs/新的普通目录
python3 experiments/analyze_into_validation.py \
  --core data/into-validation-runs/新的诊断目录 \
  --ordinary data/into-validation-runs/新的普通目录 \
  --output data/into-validation/新的分析目录
python3 experiments/plot_into_validation.py \
  --run data/into-validation/新的分析目录 \
  --output figures/into-validation/新的绘图目录
~~~

公开分析保留各案例输入、收发日志、报告 PCAP、决策、动作、源计数、最终寄存器和链路输出 PCAP。完整 loopback PCAP 与进程日志保留在原始目录，公开控制帧事件和调用字节足以分别核对相应统计口径。原始执行及派生分析源码、输入输出 SHA-256 分开归档。

图中的标记是实际收报，曲线是逐字段确认，灰区表示配置未知。图使用真实 Times New Roman，PNG 为 300 dpi，PDF 嵌入字体，绘图 CSV 来自相同日志。
